# Практика 1. Обзор системы и технический долг — отчёт

## 1. Как поднимали

При первом знакомстве со стартовым репозиторием (до того, как чинили) разворачивание
**не прошло одной командой**, хотя по методичке ожидалось «почти работает»:

1. Первый запуск `docker compose up -d` в Docker Desktop упал с ошибкой снапшоттера
   (`failed call to UtimesNanoAt ... no such file or directory`) — это проблема окружения
   (Docker Desktop), не проекта; повторный запуск прошёл нормально.
2. В логах `php` обнаружился `Fatal error: Uncaught Error: Failed opening required
   '/var/www/html/vendor/autoload.php'` (`artisan:10`, затем и `public/index.php:18`) —
   `vendor/` в образе не было, а `composer install` при сборке не запускался: исходники
   приезжают через bind-mount уже после сборки образа.
3. Следом — `file_get_contents(/var/www/html/.env): Failed to open stream` при
   `php artisan key:generate` — файла `.env` не было вообще, только `.env.example`.
4. В `.env.example` был прописан `DB_CONNECTION=sqlite`, при этом `docker-compose.yml`
   поднимает отдельный контейнер `mysql` и прокидывает в `php` переменные для MySQL —
   драйвер БД никто не переключал ни в `.env`, ни в `docker-compose.yml`.

**Что почитали:** добавили в `services/php/Dockerfile` бинарник composer
(`COPY --from=composer:2.8.4 ...`) и вызов `composer install` в
`docker-entrypoint.sh` при первом старте контейнера (см. коммит
«Исправлен Dockerfile и docker-entrypoint.sh»); в README прописали явный шаг
копирования `.env.example → .env` и ручную правку `DB_CONNECTION=mysql`.
Точную хронологию по времени двух прогонов — см. раздел 6 (учение 1).

Что проверяет каждая проверка:

| Проверка | Как |
|---|---|
| лента | `GET /`, код 200 + подстрока «Лента объявлений» в теле |
| страница входа / регистрации / список пользователей / REST-API документация | `GET`, ожидается код 200 |
| MySQL отвечает | `docker compose exec mysql mysqladmin ping -h localhost` внутри контейнера |
| регистрация | `POST /register` с CSRF-токеном и данными формы, затем `GET /ads/create` должен отдать 200 (сессия залогинена) |
| вход паролем | `POST /logout`, затем `POST /login` тем же email/паролем, снова проверка `GET /ads/create` → 200 |
| вход через GitHub | `GET /auth/github`, ожидается 302 с редиректом на `github.com` |
| подача объявления | `POST /ads` с данными формы, затем проверка, что созданное объявление видно на своей странице |
| поиск | `GET /?q=<заголовок объявления>`, заголовок должен быть в теле ответа |
| просмотр объявления | `GET /ads/{id}`, описание объявления должно быть в теле |
| комментарий | `POST /ads/{id}/comments`, затем текст комментария должен появиться на странице объявления |

## 5. Решения

Пять записей — `docs/adr/0001…0005.md`:

1. **Два сервиса (PHP + Python) вместо одного** — унаследовано с Курса 1, реального
   требования под это нет; отвергнута альтернатива «всё на одном стеке».
2. **Одна общая MySQL на оба сервиса** — оба сервиса подключаются к одному инстансу
   напрямую; отвергнуты своя база с синхронизацией событиями и доступ через HTTP к `php`.
3. **Вход через сессии + GitHub OAuth, без JWT** — стандартная SSR-схема Laravel;
   отвергнут JWT (нет отдельного клиента, которому он нужен).
4. **Docker Compose на одном хосте вместо оркестратора** — под явное железо и бюджет
   Виктора; отвергнут Kubernetes (нет экспертизы и лишних узлов).
5. **Узкое место — единственный MySQL** — гипотеза до замеров под нагрузкой; на базу
   завязаны данные, сессии, кэш и очередь одновременно; отвергнуты nginx и Redis как
   кандидаты.

**Самое сомнительное — решение №2 (общая база).** Оно само себя называет «классическим
анти-паттерном» в разделе «Следствия»: `api` никак не защищён от изменений схемы, которые
делает `php`, а вся система (данные + сессии + кэш + очередь) висит на одном инстансе без
какого-либо резерва. Альтернативы (события, HTTP-доступ через `php`) были реально
рассмотрены и отвергнуты по срокам курса, а не потому что они хуже по существу — то есть
это осознанный компромисс ради скорости, а не техническая необходимость, и он же прямо
назван местом, которое лечится в теме 10.

## 7. Учение 2 (перезагрузка)

Команда после `sudo reboot`: `cd ~/WA2-tasks && docker compose up -d && ./smoke.sh`.

**Что не поднялось само:** ничего — `docker compose up -d` показал все пять контейнеров
уже в состоянии `Running` (политика `restart: unless-stopped` и healthcheck успели
поднять их сами, ещё до ручной команды). `smoke.sh` сразу отдал «всё зелёное».

**Что добавили заранее (до перезагрузки), чтобы это сработало:**
- `restart: unless-stopped` у всех пяти сервисов (`nginx`, `php`, `api`, `mysql`, `redis`);
- healthcheck у `mysql` (`mysqladmin ping`) и у `redis` (`redis-cli ping`);
- `depends_on` с `condition: service_healthy` у `php` и `api` (ждут и `mysql`, и `redis`).

**Итоговое время:** 0:15,46 — при требовании ≤ 10 минут.

## 8. Долг

Полная таблица — `TECH_DEBT.md`, 10 пунктов.

**Три самых опасных, на мой взгляд:**

1. **Пароль от MySQL зашит в коде** (`services/api/app/main.py:18`) — прямой риск утечки
   в момент, когда репозиторий передаётся Виктору или кому-то ещё; ровно то, о чём
   заказчик просил предупредить заранее.
2. **Синхронная рассылка письма всем пользователям в цикле** при создании объявления
   (`services/php/app/Http/Controllers/AdController.php:57-63`) — чем больше
   пользователей приведёт реклама Виктора, тем дольше будет висеть каждый `POST /ads`;
   это единственный пункт долга, который становится опаснее ровно от того, ради чего
   Виктор всё это затеял (роста аудитории).
3. **Клик по категории ищет по названию, а не фильтрует** (`feed.blade.php:19` +
   `AdController.php:19-24`) — единственный из долга пункт, который прямо сейчас
   работает не так, как ожидает обычный пользователь, и это будет видно с первого дня
   рекламной кампании.
