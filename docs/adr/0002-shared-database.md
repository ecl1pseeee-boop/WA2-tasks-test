# 2. Одна общая база на оба сервиса

## Контекст
`php` и `api` — два независимых процесса, но обоим нужны
объявления: `php` их создаёт , `api` их отдаёт
(`GET /api/feed`). В сообщении Виктора было сказано: «базу не меняйте — какая есть,
такая есть» — то есть MySQL зафиксирована.

## Решение
Один инстанс MySQL (`mysql` в `docker-compose.yml`), к которому
оба сервиса подключаются напрямую своими средствами: `php` — через
Eloquent/миграции Laravel, `api` — SQL-запросами
через `pymysql`.

## Отвергнутые альтернативы
- Своя база у `api`, синхронизация событиями или вызовами к `php`.
  Правильный вариант для развязанных сервисов, но для учебного MVP 
  на одном сервере это лишняя инфраструктура: очередь событий, обработка 
  рассинхрона. По срокам не взяли.
- `api` ходит за данными в `php` по HTTP, а не в базу напрямую. Проще,
  чем через события, и убирало бы связанность через схему БД. Не взяли,
  потому что прямой SQL быстрее написать для учебного проекта. Сроки курса 
  были малы, нужен был быстрый результат ценой скрытой зависимости.

## Следствия
Классический анти-паттерн: `api` не защищён от изменений, 
которые делает `php`. `php` использует ту же MySQL ещё и 
под сессии, кэш и очередь — вся система завязана на один инстанс базы
без какого-либо резерва.

## Статус
Принято, с известным сроком пересмотра — документ 8 прямо называет тему
10 («события и развязка сервисов») местом, где это лечится.
