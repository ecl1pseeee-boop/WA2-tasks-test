# 4. Docker Compose на одном хосте вместо оркестратора

## Контекст
Виктор прямо назвал железо: один VPS, 2 ядра, 4 ГБ памяти, 80 ГБ диска,
бюджет ~10 тыс. в месяц. Резерва он не покупал — выбрал один
сервер. Пять сервисов (nginx, php, api, mysql, redis) нужно поднимать и
обновлять как единое целое.

## Решение
`docker-compose.yml` в корне репозитория поднимает все пять контейнеров
на одной машине одной командой (`docker compose up -d`).

## Отвергнутые альтернативы
- Kubernetes. Даёт скользящие обновления,
  автоперезапуск, масштабирование по узлам. Не взяли. У студентов нет опыта 
  опыта работы с ним и понимания технологии. Проект был учебный и целью было изучить
  Docker хотя бы. Также kuberу
  нужен как минимум несколько узлов или управляемый облачный кластер, это
  сильно дороже одного VPS и требует экспертизы,
  которой по вводным у Виктора и у нас на этой неделе нет.
- Голые процессы / systemd-юниты без контейнеров. Дешевле по
  ресурсам, но теряется воспроизводимость (разные версии PHP/Python на
  хосте и в разработке) и изоляция зависимостей. Не взяли — Виктор прямо
  просил «разворачивается по инструкции, без обращений к автору»,
  а это проще гарантировать контейнерами с зафиксированными версиями.

## Следствия
Поднимается одной командой, что и требовал заказчик. Обратная сторона —
никакой отказоустойчивости: `restart: unless-stopped` и healthcheck
переживут падение процесса внутри контейнера, но не
падение самого сервера. При отказе узла система лежит, пока админ не
поднимет её руками — это прямое следствие выбора Виктора 
и было явно проговорено ему в письме.
